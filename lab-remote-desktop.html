Setting Up Remote Desktop Between My DC and Client (Like an IT Tech Would)

Next thing on my list after the DNS mess: Remote Desktop. This is probably one of the most "you'll do this every single day" tasks in help desk, so I wanted to actually set it up the right way instead of just flipping a switch and calling it done.

The idea I had in my head: imagine a user calls in with a problem, and instead of walking over to their desk you just remote in and fix it. Sounds simple, but there's a right way and a lazy way to do it. I wanted to do it the right way — client has to explicitly allow it, and only the right person should be able to connect in. Here's how I set the whole thing up and actually proved it worked.

// Step 1: Turn on Remote Desktop on the client

Started on CLIENT01, my Windows 10 box. Settings → System → Remote Desktop, flip the toggle. Windows doesn't just let you turn it on though — it makes you confirm first, since you're basically opening a door into the machine.

CLIENT01 — confirming "Enable Remote Desktop?" before turning it on. Makes sense Windows double-checks this one.
Toggle's on. Windows gives you the PC name to connect to — CLIENT01.corp.local — which is what I'll need from the other end.

// Step 2: Don't just leave it on Administrator

Here's the thing — by default, whoever's in the local Administrators group can already connect. But I didn't want to lean on that. In a real job you're usually connecting with your own account, not some shared admin login. So I went into "Select users that can remotely access this PC" and added my actual domain user, CORP\smith, by name.

CORP\smith added to the Remote Desktop Users list. The dialog reminds you CORP\Administrator already has access — good to know, not something I wanted to rely on though.
Why I bothered with this: It's a small thing, but scoping access to a specific account instead of just riding on default admin rights is basic least-privilege thinking. Habit worth building early.

// Step 3: Connect from the other machine

Hopped over to DC01 (my "admin machine" for this exercise) and opened Remote Desktop Connection, pointed it at CLIENT01's IP — 192.168.1.20.

"Securing remote connection..." — the connection handshake happening before it asks for credentials.

// Step 4: The certificate warning (don't panic, it's expected)

Right after logging in, I got hit with a certificate warning. First time you see this it looks alarming, but it's totally expected in a lab setup — CLIENT01 doesn't have a cert from a trusted CA, so RDP just falls back to a self-signed one that Windows can't vouch for.

"The identity of the remote computer cannot be verified" — but the certificate name matches CLIENT01.corp.local, which is exactly the machine I was trying to reach.

I still checked the certificate name against the machine I was actually trying to connect to before hitting Yes. Good habit to build now, because on a real network that's exactly the kind of check that catches something sketchy before it's a problem.

// Step 5: Proving I actually landed on the right machine

Once I was in, I had a full remote session sitting on CLIENT01's desktop. To make sure I wasn't just staring at a local window, I popped open Command Prompt and ran hostname.

Connected — this is CLIENT01's desktop, viewed from DC01. Title bar shows the IP I'm remoted into: 192.168.1.20.
hostname says CLIENT01. Confirmed — I'm actually inside the remote machine, not just looking at some window that looks like it.
C:\Users\Administrator>hostname
CLIENT01

C:\Users\Administrator>

// What I took away from this

  • Turning RDP on is the easy 10% — deciding who's actually allowed in is the part that matters. Adding a named user instead of leaning on default admin access is a small habit that pays off.
  • Don't just click through certificate warnings without looking. Checking the name against the machine you meant to hit takes two seconds and it's the kind of thing that saves you one day.
  • Always double check where you actually landed. Running hostname is such a small thing but it's saved me from confusion before, especially once you're juggling a few RDP windows at once.
  • This is one of those "you'll do it constantly" tasks in help desk, so I wanted the muscle memory for the whole flow, not just clicking Connect and hoping.
